# Verilog 模块结构与连线管理技术选型分析文档

日期：2026-05-13

## 1. 选型结论

推荐采用：

```text
Excel/XLSX
  <-> Python 转换器
  <-> YAML/JSON 结构化 IR
  <-> Schema + 语义校验器
  <-> Verilog 生成器 / 图形生成器 / React Flow 可视化编辑器

已有 Verilog/SystemVerilog
  <-> 接口提取器
  <-> YAML/JSON 结构化 IR
```

核心原则：

1. 结构化 IR 是主数据源，Verilog 是生成物。
2. Excel 是人类批量编辑入口，不直接作为唯一真源。
3. 图形界面是可视化编辑入口，不让图形文件独占设计真源。
4. AI 修改 IR，不直接维护生成后的 Verilog 代码。
5. Schema 只能保证结构合法，硬件语义必须由专用校验器补充。

## 2. 编程语言选型

| 方向 | 候选 | 推荐 | 原因 |
| --- | --- | --- | --- |
| 数据转换 | Python / Node.js / Go | Python | `openpyxl`、`pandas`、`pydantic`、`jinja2` 生态成熟，适合 Excel、校验和代码生成 |
| 前端界面 | React / Vue / Svelte | React | React Flow 生态成熟，节点连线编辑器实现成本低 |
| 后端服务 | FastAPI / Flask / Express | FastAPI | Python 技术栈统一，类型声明清晰，适合后续提供导入导出和校验 API |
| 命令行工具 | Python argparse / Typer / Click | Typer | 适合快速构建 `import/export/validate/generate` 子命令 |
| Verilog 接口提取 | PyVerilog / hdlConvertor / Surelog / slang | 分阶段选择 | 第一阶段提取 module、parameter、port、width；复杂 SystemVerilog 后续评估 slang 或 Surelog |

推荐第一阶段技术栈：

```text
Python + Typer + Pydantic + OpenPyXL + Jinja2 + PyYAML
```

推荐第二阶段技术栈：

```text
React + TypeScript + React Flow + FastAPI
```

## 3. 结构化文件格式选型

### 3.1 候选格式对比

| 格式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| JSON | 程序交换友好，前端天然支持，JSON Schema 成熟 | 人类手写可读性一般，注释支持差 | 适合作为机器交换格式 |
| YAML | 人类可读性好，适合 AI 和人工局部修改 | 解析细节比 JSON 复杂，需要规范子集 | 适合作为主 IR 或人工维护格式 |
| CSV | 简单，Excel 友好，Git diff 清晰 | 多表关系表达弱，类型信息弱 | 适合导入导出，不适合完整主 IR |
| XLSX | 工程师熟悉，批量编辑方便 | Git diff 差，自动合并差 | 适合作为人类编辑入口 |
| XML/IP-XACT | 硬件领域标准化程度高 | 复杂，人类编辑体验差，落地成本高 | 后续可选，不建议第一阶段使用 |
| GraphML | 图结构表达能力强，yEd 友好 | 对 AI 和脚本偏啰嗦 | 适合可视化交换，不适合作为主 IR |

### 3.2 推荐格式

第一阶段推荐：

```text
design.yaml        人类和 AI 友好的主 IR
design.schema.json IR 结构约束
design.xlsx        Excel 导入导出文件
```

后续扩展：

```text
design.json        前端和 API 交换格式
layout.json        React Flow 节点位置和视图状态
design.graphml     yEd 兼容图形交换格式
```

### 3.3 IR 建议模型

Verilog 模块结构更接近关系模型，而不是单纯树模型。推荐拆成以下实体：

| 实体 | 说明 |
| --- | --- |
| module | 模块定义 |
| port | 模块端口 |
| instance | 模块实例 |
| net | 内部信号或总线 |
| connection | 实例端口与 net 的连接关系 |
| parameter | 模块参数与实例参数覆盖 |
| attribute | 注释、分组、布局、标签等扩展信息 |

示例：

```yaml
modules:
  - name: alu
    description: arithmetic logic unit
    ports:
      - name: clk
        direction: input
        width: 1
      - name: a
        direction: input
        width: 32
      - name: y
        direction: output
        width: 32

instances:
  - name: u_alu
    module: alu

nets:
  - name: clk
    width: 1
  - name: alu_a
    width: 32
  - name: alu_y
    width: 32

connections:
  - instance: u_alu
    port: clk
    net: clk
  - instance: u_alu
    port: a
    net: alu_a
  - instance: u_alu
    port: y
    net: alu_y
```

## 4. 图形界面选型

### 4.1 候选方案

| 方案 | 优点 | 缺点 | 适用阶段 |
| --- | --- | --- | --- |
| Mermaid | 文档友好，生成简单，适合快速预览 | 编辑能力弱，不适合复杂端口级交互 | 第一阶段预览 |
| Graphviz DOT | 自动布局强，适合大型拓扑图 | 交互编辑弱 | 第一阶段预览 |
| yEd + GraphML | 成熟桌面图编辑器，支持 GraphML | 双向同步需要转换器 | 第二阶段可选 |
| React Flow | 可高度定制，天然 nodes/edges 数据模型 | 需要开发前端 | 第二阶段主推 |
| Draw.io | 人类画图方便 | 数据语义校验弱，自动化维护较麻烦 | 仅作为辅助 |
| Node-RED | 原型快 | UI 风格和 EDA 场景不完全匹配 | 不推荐作为正式界面 |

### 4.2 推荐策略

第一阶段：

```text
IR -> Mermaid / Graphviz
```

用于快速验证结构数据是否正确。

第二阶段：

```text
IR <-> React Flow JSON
```

用于实现真正的可视化编辑器。

## 5. 前端组件库选型

推荐：

| 类型 | 推荐 | 用途 |
| --- | --- | --- |
| 节点连线编辑 | React Flow | 模块实例节点、端口 handle、信号连线 |
| UI 基础组件 | Ant Design / MUI / shadcn/ui | 表格、抽屉、弹窗、表单 |
| 数据表格 | TanStack Table / AG Grid | 端口表、连接表、参数表 |
| 状态管理 | Zustand | 管理当前设计、选择状态、编辑历史 |
| 表单校验 | React Hook Form + Zod | 模块、端口、连接编辑表单 |
| 图标 | lucide-react | 工具栏和操作按钮 |

推荐组合：

```text
React + TypeScript + React Flow + Zustand + TanStack Table + Zod
```

如果追求企业级表格能力，可将 TanStack Table 替换为 AG Grid。

## 6. 后端与脚本组件选型

| 组件 | 推荐库 | 用途 |
| --- | --- | --- |
| CLI | Typer | 命令行入口 |
| 数据模型 | Pydantic | IR 类型定义和基础校验 |
| Schema | JSON Schema | AI 输出约束和跨语言校验 |
| Excel | openpyxl | XLSX 读写 |
| 表格处理 | pandas | 批量转换和数据清洗 |
| YAML | PyYAML / ruamel.yaml | 读取和输出 IR |
| 模板生成 | Jinja2 | Verilog/SystemVerilog 生成 |
| Verilog 接口提取 | PyVerilog / hdlConvertor / slang | 从已有 RTL 提取模块端口、参数和位宽信息 |
| API 服务 | FastAPI | 前端调用导入、导出、校验、生成 |
| 测试 | pytest | 转换器、校验器、生成器测试 |

## 7. 校验能力选型

需要三层校验：

| 层级 | 内容 | 技术 |
| --- | --- | --- |
| Schema 校验 | 字段是否存在、类型是否正确、枚举是否合法 | JSON Schema / Pydantic |
| 引用校验 | 模块、实例、端口、net 是否存在 | Python 校验器 |
| 硬件语义校验 | 位宽、方向、多驱动、悬空、bus slice、clock/reset domain | Python 规则引擎 |

第一阶段建议实现的规则：

1. 实例引用的模块必须存在。
2. 连接引用的实例和端口必须存在。
3. input 端口不能作为 net 的驱动源。
4. output 端口不能被多个输出同时驱动同一 net，除非显式标注允许。
5. 端口位宽和 net 位宽必须一致，或显式配置 slice/extend/truncate。
6. 必填端口不能悬空。

## 9. 分阶段选型建议

| 阶段 | 目标 | 技术 |
| --- | --- | --- |
| P0 | 设计数据模型和样例 | YAML、JSON Schema |
| P1 | 打通 Excel/Verilog 接口提取到 IR 到 Verilog | Python、openpyxl、pydantic、jinja2、Verilog parser |
| P2 | 增加校验和图形预览 | pytest、Mermaid、Graphviz |
| P3 | Web 可视化编辑 | React、TypeScript、React Flow、FastAPI |
| P4 | 与现有 RTL/EDA 流程集成 | slang/Surelog、CI、生成报告 |

## 10. 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| IR 模型设计过早绑定 UI | 后续难扩展 | 核心 IR 与 layout 数据分离 |
| 只做 Schema 不做语义校验 | 生成错误 Verilog | 建立硬件规则校验器 |
| Excel 与 IR 双向同步冲突 | 数据覆盖或丢失 | 导入前生成 diff 和校验报告 |
| 单个大 JSON 文件膨胀 | Git diff 和 AI 修改困难 | 支持按模块拆分 YAML |
| 前端优先导致核心模型不稳定 | 开发成本浪费 | 先完成 CLI 闭环，再做 React Flow |
| Verilog 解析器不支持复杂语法 | 接口提取不完整 | 第一阶段只承诺提取例化所需接口信息，对复杂宏和接口类型输出告警 |
