# Verilog 模块结构与连线管理技术选型分析文档

日期：2026-05-13

## 1. 选型结论

推荐采用：

```text
Excel/XLSX
  <-> Python 转换器
  <-> YAML/JSON 结构化 IR
  <-> Schema + 语义校验器
  <-> Verilog 生成器 / 语法检查器 / React Flow 只读预览 / 后续 React Flow 可视化编辑器

已有 Verilog-2005
  <-> Pyverilog 接口提取器
  <-> YAML/JSON 结构化 IR

算法定点化框图 + 信号属性表格
  <-> 亿图 SVG 导入器 + openpyxl 表格导入器
  <-> YAML/JSON 结构化 IR
```

核心原则：

1. 结构化 IR 是主数据源，Verilog 是生成物。
2. Excel 是人类批量编辑入口，不直接作为唯一真源。
3. React Flow JSON 是第一阶段拓扑查看和后续图形编辑之间的图数据桥梁。
4. 算法框图负责连接关系，信号属性表负责位宽和定点属性，两者导入后合并进 IR。
5. AI 修改 IR，不直接维护生成后的 Verilog 代码。
6. Schema 只能保证结构合法，硬件语义和定点语义必须由专用校验器补充。
7. 生成的 Verilog `.v` 必须经过独立语法检查工具验证，不能只依赖生成器自身判断。

## 2. 编程语言选型

| 方向 | 候选 | 推荐 | 原因 |
| --- | --- | --- | --- |
| 数据转换 | Python / Node.js / Go | Python | `openpyxl`、`pandas`、`pydantic`、`jinja2` 生态成熟，适合 Excel、校验和代码生成 |
| 前端界面 | React / Vue / Svelte | React | React Flow 生态成熟，节点连线编辑器实现成本低 |
| 后端服务 | FastAPI / Flask / Express | FastAPI | Python 技术栈统一，类型声明清晰，适合后续提供导入导出和校验 API |
| 命令行工具 | Python argparse / Typer / Click | Typer | 适合快速构建 `import/export/validate/generate` 子命令 |
| Verilog 接口提取 | Pyverilog / Verible / slang | Pyverilog | 第一阶段目标是 Verilog-2005 接口提取，Pyverilog 可直接在 Python 流水线中解析 AST |
| 算法框图导入 | 亿图 SVG / `.eddx` | SVG 优先 | SVG 是 XML 文本，第一阶段更容易提取文本、节点、连接线和信号名；`.eddx` 保留为样例验证对象 |
| 拓扑查看 | React Flow / Mermaid / Graphviz DOT | React Flow 只读预览 | 第一阶段只读查看，第二阶段平滑升级为编辑器 |
| 生成代码语法检查 | Icarus Verilog / Verilator / Yosys | Icarus Verilog | 第一阶段生成 Verilog-2005 `.v`，Icarus Verilog 适合做轻量编译式语法检查；Verilator 后续作为 lint 增强 |

推荐第一阶段技术栈：

```text
Python + Typer + Pydantic + OpenPyXL + PyYAML + Pyverilog + Jinja2
Icarus Verilog
React + TypeScript + React Flow
```

推荐第二阶段技术栈：

```text
React + TypeScript + React Flow + FastAPI
```

## 3. 结构化文件格式选型

### 3.1 候选格式对比

| 格式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| JSON | 程序交换友好，前端天然支持，JSON Schema 成熟 | 人类手写可读性一般，注释支持差 | 适合作为机器交换格式 |
| YAML | 人类可读性好，适合 AI 和人工局部修改 | 解析细节比 JSON 复杂，需要规范子集 | 适合作为主 IR 或人工维护格式 |
| CSV | 简单，Excel 友好，Git diff 清晰 | 多表关系表达弱，类型信息弱 | 适合导入导出，不适合完整主 IR |
| XLSX | 工程师熟悉，批量编辑方便 | Git diff 差，自动合并差 | 适合作为人类编辑入口 |
| XML/IP-XACT | 硬件领域标准化程度高 | 复杂，人类编辑体验差，落地成本高 | 后续可选，不建议第一阶段使用 |
| SVG | 亿图可导出，XML 文本格式，便于第一阶段解析 | 连接语义需要结合样例验证 | 第一阶段亿图框图导入首选 |
| `.eddx` | 亿图原生格式，可能保留更多编辑语义 | 需要样例确认内部结构和可解析性 | 第一阶段保留为备选验证 |
| React Flow JSON | 前端编辑器天然格式，nodes/edges 结构清晰 | 依赖自研前端约定 | 第一阶段拓扑查看和第二阶段编辑的统一图数据格式 |
| draw.io XML | 人类画图方便，工具普及 | 语义约束弱，解析规则需约定 | 适合辅助导入，不建议作为主格式 |

### 3.2 推荐格式

第一阶段推荐：

```text
design.yaml        人类和 AI 友好的主 IR
design.schema.json IR 结构约束
design.xlsx        Excel 导入导出文件
algo.svg           亿图导出的算法框图
fixed_signals.xlsx 算法定点化信号属性表
graph.reactflow.json 第一阶段只读拓扑预览和后续编辑器的图数据
```

后续扩展：

```text
design.json        前端和 API 交换格式
layout.json        React Flow 节点位置和视图状态
algo.eddx          亿图原生文件，待样例验证后决定是否直接解析
```

### 3.3 IR 建议模型

Verilog 模块结构更接近关系模型，而不是单纯树模型。推荐拆成以下实体：

| 实体 | 说明 |
| --- | --- |
| module | 模块定义 |
| port | 模块端口 |
| instance | 模块实例 |
| net | 内部信号或总线 |
| connection | 实例端口与 net 的连接关系 |
| parameter | 模块参数与实例参数覆盖 |
| attribute | 注释、分组、布局、标签等扩展信息 |
| algorithm_block | 算法定点化框图中的算子或功能块 |
| signal_attribute | 信号位宽、符号、小数位、量化、舍入和饱和属性 |

示例：

```yaml
modules:
  - name: alu
    description: arithmetic logic unit
    ports:
      - name: clk
        direction: input
        width: 1
      - name: a
        direction: input
        width: 32
      - name: y
        direction: output
        width: 32

instances:
  - name: u_alu
    module: alu

nets:
  - name: clk
    width: 1
  - name: alu_a
    width: 32
  - name: alu_y
    width: 32

connections:
  - instance: u_alu
    port: clk
    net: clk
  - instance: u_alu
    port: a
    net: alu_a
  - instance: u_alu
    port: y
    net: alu_y

signal_attributes:
  - name: alu_a
    width: 32
    signed: true
    frac_width: 1
    fixed_format: s(32,1)
```

## 4. 图形界面选型

### 4.1 候选方案

| 方案 | 优点 | 缺点 | 适用阶段 |
| --- | --- | --- | --- |
| React Flow 只读预览 | 数据模型与后续编辑器一致，支持节点、边、端口 handle、坐标和分组 | 需要少量前端开发 | 第一阶段主选 |
| Mermaid | 文档友好，生成简单 | 编辑能力弱，不适合复杂端口级交互 | 可选文档导出 |
| Graphviz DOT | 自动布局强，适合静态大图 | 与后续人工编辑模型不一致 | 不作为第一阶段主方案 |
| yEd + GraphML | 成熟桌面图编辑器，支持 GraphML | 双向同步需要转换器 | 第二阶段可选 |
| React Flow 编辑器 | 可高度定制，天然 nodes/edges 数据模型 | 需要开发编辑交互和保存逻辑 | 第二阶段主推 |
| Draw.io | 人类画图方便 | 数据语义校验弱，自动化维护较麻烦 | 仅作为辅助 |
| Node-RED | 原型快 | UI 风格和 EDA 场景不完全匹配 | 不推荐作为正式界面 |

### 4.2 推荐策略

第一阶段：

```text
亿图 SVG + 定点表格 -> IR
IR -> React Flow JSON -> React Flow 只读预览
```

用于快速验证结构数据和算法连接数据是否正确，同时为第二阶段图形编辑保留同一套图数据结构。

第二阶段：

```text
IR <-> React Flow JSON
```

用于实现真正的可视化编辑器。

## 7. 校验能力选型

需要三层校验：

| 层级 | 内容 | 技术 |
| --- | --- | --- |
| Schema 校验 | 字段是否存在、类型是否正确、枚举是否合法 | JSON Schema / Pydantic |
| 引用校验 | 模块、实例、端口、net、算法 block、信号属性是否存在 | Python 校验器 |
| 硬件语义校验 | 位宽、方向、多驱动、悬空、bus slice、clock/reset domain | Python 规则引擎 |
| 定点语义校验 | signed、width、frac_width、定点格式是否一致 | Python 规则引擎 |

第一阶段建议实现的规则：

1. 实例引用的模块必须存在。
2. 连接引用的实例和端口必须存在。
3. input 端口不能作为 net 的驱动源。
4. output 端口不能被多个输出同时驱动同一 net，除非显式标注允许。
5. 端口位宽和 net 位宽必须一致，或显式配置 slice/extend/truncate。
6. 必填端口不能悬空。
7. 算法框图中的每条信号边应能匹配到表格中的信号属性。
8. 定点属性应满足 `width > 0`、`frac_width >= 0`、`frac_width <= width` 等基本约束。

## 8. 生成代码语法检查选型

### 8.1 候选工具对比

| 工具 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Icarus Verilog | 支持 Verilog 1995/2001/2005，命令行简单，适合检查生成的 `.v` 是否能编译 | lint 能力不如 Verilator，主要定位是编译/仿真工具 | 第一阶段主选 |
| Verilator | `--lint-only` 适合做 lint，诊断能力强，后续可检查更多风格和可综合性问题 | 对代码风格更严格，初期可能引入较多非语法类 warning 处理成本 | 第二阶段 lint 增强 |
| Yosys | 可用于综合流程和结构检查 | 官方资料提示不应依赖 `read_verilog` 作为语法检查工具 | 不作为第一阶段语法检查主工具 |

### 8.2 推荐策略

第一阶段使用 Icarus Verilog 对生成 `.v` 做编译式语法检查：

```bash
iverilog -g2005 -t null -o build/syntax_check.out generated/top.v
```

策略说明：

1. `-g2005` 对齐第一阶段 Verilog-2005 目标。
2. `-t null` 用于只检查编译前端，不生成仿真产物。
3. 语法检查失败时，生成流程应返回 ERROR，并保留 Icarus Verilog 的错误日志。
4. 第二阶段可增加 Verilator `--lint-only` 作为 lint 增强，但不替代第一阶段的 Icarus Verilog 基础检查。

## 10. 分阶段选型建议

| 阶段 | 目标 | 技术 |
| --- | --- | --- |
| P0 | 设计数据模型和样例 | YAML、JSON Schema |
| P1 | 打通 Excel/Verilog 接口提取/算法框图表格到 IR 到 Verilog，并完成生成代码语法检查 | Python、openpyxl、pydantic、jinja2、Pyverilog、SVG parser、Icarus Verilog |
| P2 | 增加校验和只读图形预览 | pytest、React、TypeScript、React Flow |
| P3 | Web 可视化编辑 | React、TypeScript、React Flow、FastAPI |
| P4 | 与现有 RTL/EDA 流程集成 | Verilator lint、slang/Surelog、CI、生成报告 |

## 11. 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| IR 模型设计过早绑定 UI | 后续难扩展 | 核心 IR 与 layout 数据分离 |
| 只做 Schema 不做语义校验 | 生成错误 Verilog | 建立硬件规则校验器 |
| Excel 与 IR 双向同步冲突 | 数据覆盖或丢失 | 导入前生成 diff 和校验报告 |
| 单个大 JSON 文件膨胀 | Git diff 和 AI 修改困难 | 支持按模块拆分 YAML |
| 前端优先导致核心模型不稳定 | 开发成本浪费 | 先完成 CLI 闭环，再做 React Flow |
| Verilog 解析器不支持复杂语法 | 接口提取不完整 | 第一阶段只承诺提取例化所需接口信息，对复杂宏和接口类型输出告警 |
| 算法框图和位宽表不一致 | 连接存在但位宽缺失，或表格信号无人使用 | 导入阶段生成匹配报告，缺失项作为 ERROR 或 WARNING |
| 亿图 SVG 连接语义不足 | 无法可靠恢复 block/edge 关系 | 要求提供实际 SVG 样例验证；必要时回退评估 `.eddx` |
| 第一阶段前端工作膨胀 | 只读预览变成编辑器开发 | 严格限制第一阶段 React Flow 只读，不实现拖拽保存和连线编辑 |
| 只做字符串级生成检查 | 生成代码看似完整但存在语法错误 | 使用 Icarus Verilog 对生成 `.v` 做独立语法检查 |
| 语法检查工具 warning 过多 | 初期阻塞生成流程 | 第一阶段只将 Icarus Verilog 编译错误作为 ERROR，lint warning 进入后续阶段处理 |
